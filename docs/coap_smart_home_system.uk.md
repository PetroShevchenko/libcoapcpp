# CoAP Smart Home — архітектура та концепція системи

> **Статус:** концепція / початкова специфікація (v0.2)  
> **Дата:** 17 жовтня 2026  
> **Основа:** `libcoapcpp`, OpenWrt, PlatformIO  
> **Призначення документа:** узгодити компоненти, їхні межі відповідальності та послідовність створення відкритої IoT-платформи.  
> **Зміни відносно v0.1:** враховано зауваження з `coap_smart_home_review.md` — самореєстрація вузлів замість multicast-пошуку, профіль пристрою на основі стандартів (CoRE Link Format, SenML), стокова прошивка з конфігурацією під час роботи, provisioning через Web Serial, pull-OTA, локальна збірка на ПК замість Build Server, зафіксована модель паралелізму gateway, уточнена модель безпеки та дорожня карта.

## 1. Огляд

**CoAP Smart Home** — модульна, локально керована open-source платформа для моніторингу датчиків, керування виконавчими пристроями та життєвим циклом прошивок. Основним шлюзом може бути маршрутизатор з OpenWrt, але архітектура залишається переносимою на звичайний Linux (Ubuntu, Debian, Raspberry Pi OS).

Типовий сценарій: користувач купує ESP32 або Raspberry Pi Pico W, підключає підтримуваний датчик, відкриває у браузері сторінку «Додати пристрій», записує стокову прошивку через USB прямо з браузера, вказує Wi-Fi і піни датчиків. Пристрій сам реєструється на gateway і з'являється на дашборді з вимірюваннями та керуванням. Компілювати нічого не потрібно. Оновлення стокових прошивок встановлюються через OTA; власні прошивки розробник збирає локально на своєму ПК.

### 1.1 Цілі

- Робота датчиків і керування пристроями **без інтернету та без хмарної залежності**.
- Просте встановлення шлюзу на OpenWrt; альтернативно — Linux.
- **Без компіляції для типових сценаріїв**: одна стокова прошивка на плату, датчики й піни налаштовуються під час роботи.
- Мінімальне програмування для розробника: високорівнева оболонка **SmartNode SDK** над `libcoapcpp`.
- Відкритий CoAP-інтерфейс на основі стандартів IETF; можливість створювати сумісні пристрої без SmartNode SDK.
- Автоматична поява пристроїв через самореєстрацію, підтримка CoAP Observe.
- Єдиний вебінтерфейс для вимірювань, керування, конфігурації, першого прошивання та OTA.
- Компіляція власних прошивок **локально на ПК користувача** (PlatformIO або Docker-збирач), без toolchain на роутері і без окремого сервера збирання.

### 1.2 Нецілі першої версії

Не передбачається одразу:

- замінити Home Assistant; реалізувати Zigbee, Matter, відеоспостереження, мобільний застосунок, складні сценарії автоматизації;
- велику історичну БД вимірювань на gateway;
- публічний або self-hosted Build Server;
- LuCI-застосунок;
- повну сумісність з OMA LwM2M (модель об'єктів і логіка оновлення запозичуються, але протокол не реалізується повністю);
- OTA для Pico W і підтримку STM32 — після стабілізації ESP32;
- десятки платформ і датчиків.

### 1.3 Ключові архітектурні рішення

| Рішення | Суть | Розділ |
|---|---|---|
| Самореєстрація вузлів | Вузол сам реєструється на gateway (CoRE Resource Directory); multicast — лише резерв | 5.2, 6 |
| Стандартний профіль пристрою | `rt`/`if`/`obs` у link-format + SenML замість власного формату | 5.1 |
| Стокова прошивка на плату | Драйвери вбудовані, конфігурація — під час роботи | 3.2 |
| Provisioning через Web Serial | Прошивка, Wi-Fi і ключ передаються з браузера по USB | 4.1 |
| Pull-OTA | Gateway повідомляє, вузол сам завантажує образ (Block2) | 6 |
| Локальна збірка | Docker-збирач на ПК + репозиторій прошивок на gateway; Build Server відсутній | 3.6 |
| Один CoAP-потік у gateway | HTTP не виконує CoAP напряму; черга команд + снапшот стану | 3.3 |
| Gateway без доступу в інтернет | Образи надходять ззовні (браузер або CLI) | 3.6 |

## 2. Загальна архітектура

```text
 ┌──────────────────────────────┐         ┌──────────────────────────────────┐
 │ Web Browser                  │         │ ПК розробника (опційно)          │
 │ Dashboard / Devices /        │         │ smartnode build / sign / upload  │
 │ Add device / Firmware        │         │ (PlatformIO або Docker-збирач)   │
 └───────┬───────────────┬──────┘         └────────────────┬─────────────────┘
         │ HTTP(S)+SSE   │ Web Serial (USB)                │ HTTP POST образ+маніфест
         │               ▼                                 │
         │      плата на USB: перше прошивання,            │
         │      Wi-Fi, адреса gateway, ключ                │
         ▼                                                 ▼
 +-----------------------------------------------------------------------+
 |                   OpenWrt Router або Linux Host                       |
 |                                                                       |
 |  +------------------------------------------------------------------+ |
 |  | coap-manager (один процес)                                       | |
 |  |  CivetWeb: REST API + SSE + статичний Web UI                     | |
 |  |      │ черга команд            ▲ снапшот стану                    | |
 |  |      ▼                         │                                  | |
 |  |  CoAP event loop (libcoapcpp, 1 потік)                           | |
 |  |   RD /rd | Registry | Observe | Control | OTA | Firmware Repo /fw| |
 |  |  State Store (RAM) + config/registry (Flash, рідкі записи)       | |
 |  +---------------------------------+--------------------------------+ |
 +------------------------------------|----------------------------------+
                                      | CoAP / UDP + DTLS-PSK
             реєстрація, heartbeat ▲  |  ▼ GET/PUT, Observe, /system/update
             GET /fw (Block2)      |  |
                        +----------+--+---------+
                        |          |            |
                  +-----v----+ +---v------+ +---v--------+
                  | ESP32    | | Pico W   | | STM32*     |
                  | стокова  | | стокова  | | власна     |
                  | прошивка | | прошивка | | збірка     |
                  +----------+ +----------+ +------------+
                                              * після 1.0, потребує мережевого модуля

 Джерела образів:  офіційні релізи (CI → GitHub/GitLab Releases) → браузер ─┐
                   локальна збірка на ПК (CLI / Docker) ─────────────────────┴─► POST /api/v1/firmware
```

**Ролі:**

- **Браузер** — HTTP-клієнт gateway; також виконує перше прошивання та provisioning через Web Serial.
- **Gateway** — HTTP-сервер (API, SSE, UI); CoAP-сервер (Resource Directory `/rd`, роздача образів `/fw`); CoAP-клієнт (запити до вузлів, Observe).
- **Вузли** — CoAP-сервери ресурсів датчиків/виконавчих пристроїв і CoAP-клієнти для реєстрації та завантаження прошивок.
- **ПК розробника** — опційне середовище збирання власних прошивок; не має прямого зв'язку з вузлами.

## 3. Компоненти

### 3.1 libcoapcpp

Самостійна C++ бібліотека реалізації CoAP. Залишається незалежною від Smart Home, OpenWrt та HTTP. Застосовується у gateway та у firmware пристроїв.

Необхідні можливості:

| Можливість | Gateway | Вузол |
|---|---|---|
| Неблокувальний клієнт, транзакції, тайм-аути, повтори | так | так (реєстрація, OTA) |
| Сервер ресурсів, CoRE Link Format (RFC 6690) | так (`/rd`, `/fw`) | так |
| Observe (RFC 7641) | клієнт | сервер |
| Block2 (RFC 7959) | сервер (роздача образів) | клієнт (завантаження образів) |
| DTLS 1.2 з PSK | так | так |
| OSCORE (RFC 8613) | після 1.0 | після 1.0 |

### 3.2 SmartNode SDK і стокова прошивка

Оболонка над `libcoapcpp`, інтегрована з PlatformIO. Приховує токени, коди CoAP, реєстрацію, link-format, SenML, OTA та мережеву логіку. SDK одночасно є основою **стокової прошивки** — тож тестується реальним продуктом.

**Що означає «універсальна прошивка».** Один бінарник для всіх MCU неможливий: ESP32 (Xtensa/RISC-V), RP2040 і STM32 (ARM Cortex-M) мають різні набори інструкцій, bootloader-и та карти Flash. Мета — не множити збірки на комбінації датчиків:

| Підхід | Кількість образів |
|---|---|
| Збірка під конфігурацію | плати × комбінації датчиків × піни — практично нескінченно |
| Конфігурація під час роботи | кількість цільових плат — умовно 10–20 на реліз |

**Три рівні вузла:**

1. **Платформний шар (HAL SDK)** — I2C, SPI, GPIO, ADC, OneWire, UART, Wi-Fi, сховище конфігурації, OTA-backend. Компілюється під кожну плату.
2. **Драйвери датчиків** — пишуться тільки через HAL і не залежать від MCU. Стоковий образ містить драйвери MVP: BME280, DHT22, DS18B20, реле, кнопка.
3. **Конфігурація** — зберігається у NVS/Flash, задається під час provisioning або через `PUT /system/config`; ресурси створюються динамічно:

```json
{
  "buses": [{"id": "i2c0", "type": "i2c", "sda": 21, "scl": 22, "freq": 400000}],
  "devices": [
    {"driver": "bme280", "bus": "i2c0", "addr": "0x76", "name": "living_room"},
    {"driver": "relay",  "pin": 5, "active_low": true, "name": "heater"}
  ]
}
```

**Опис плати (board descriptor)** постачається разом з образом: доступні піни, їхні функції (I2C/SPI/ADC/PWM), обмеження. Gateway і сторінка «Додати пристрій» перевіряють конфігурацію до запису на пристрій.

**API для розробника власної прошивки** (концептуальний):

```cpp
#include <SmartNode.h>

SmartNode node;

void setup() {
  node.begin();   // конфігурація, Wi-Fi, ключі, стокові драйвери, реєстрація на gateway
  node.addSensor("soil", "moisture", "%", [] { return read_soil(); });
  node.addSwitch("pump", [](bool on) { set_pump(on); });
}

void loop() { node.loop(); }
```

**Коли потрібна компіляція:** STM32 з малою Flash (64–128 КБ) і різноманітним тактуванням/pinmux; власна логіка користувача; рідкісні драйвери, яких немає у стоковому образі. Для цих випадків — локальна збірка (3.6).

### 3.3 CoAP Device Manager / Gateway

Один фоновий C++ процес `coap-manager`, який:

- приймає реєстрації вузлів (Resource Directory, RFC 9176) і веде реєстр за стабільним ідентифікатором `ep`, а не за IP;
- визначає online/offline за lifetime реєстрації;
- виконує GET/PUT/POST/DELETE відповідно до можливостей вузлів;
- підтримує одну Observe-підписку на ресурс, кеш останніх значень, повторну підписку після збоїв і позначку застарілих значень;
- транслює зміни стану у Web UI через SSE;
- веде локальний репозиторій прошивок, перевіряє підписи й сумісність, керує pull-OTA;
- веде журнал подій і аудит керувальних операцій;
- **не потребує доступу в інтернет**.

#### 3.3.1 Модель паралелізму

```text
 HTTP-потоки CivetWeb ──(команда у черзі)──► CoAP event loop (1 потік)
        ▲                                         │
        │                                         ▼
        └──── читання снапшоту ◄──── State Store (mutex + copy / RCU)
```

- Один потік володіє `libcoapcpp`, UDP-сокетами, таймерами, Observe-підписками й реєстром.
- HTTP-обробники **ніколи не виконують CoAP самі**: читання повертає снапшот кешу; керувальні запити кладуть команду в чергу й чекають результат з тайм-аутом або повертають `202 Accepted` з ідентифікатором операції.
- Тайм-аути CoAP не блокують HTTP.

#### 3.3.2 Зберігання

- Поточний стан і короткий кільцевий буфер вимірювань — **лише в RAM**.
- У Flash — тільки конфігурація gateway, реєстр пристроїв і ключі; записи атомарні й рідкі (за зміною, не за таймером).
- Образи прошивок — обмежена кількість останніх версій на плату; за потреби — USB-накопичувач.
- Довга історія — поза MVP; пізніше через експорт (MQTT, InfluxDB, Prometheus).

### 3.4 Web UI

Окремий адаптивний інтерфейс на HTML/CSS/JavaScript, доступний, наприклад, за `https://router.local:8443/` (адреса й порт конфігуровані).

| Сторінка | Функціональність |
|---|---|
| Dashboard | Картки кімнат/датчиків, вимірювання, стани, перемикачі; оновлення через SSE |
| Devices | Список пристроїв (`ep`, плата, версія, IP, online/offline), конфігурація датчиків |
| Add device | Перше прошивання через Web Serial, налаштування Wi-Fi і датчиків, видача ключа |
| Firmware | Репозиторій образів, імпорт офіційних релізів, завантаження локальних збірок, OTA та прогрес |
| Resource Explorer | Довільні CoAP-запити, тільки для ролі «розробник» (з етапу 0.2) |
| Settings | Конфігурація gateway, користувачі й ролі, ключі, безпека |

Оновлення стану — одразу через **Server-Sent Events** (`EventSource` у браузері), без polling. Web UI ніколи не ініціює CoAP-запит на кожне оновлення сторінки.

### 3.5 HTTP-сервер

**Рішення:** **CivetWeb** вбудовується в `coap-manager` — переносимий між Linux і OpenWrt, підтримує тривалі з'єднання для SSE та HTTPS.

Відхилені альтернативи:

- **uHTTPd + CGI** — процес на кожен запит не підходить для SSE і спільного стану; uHTTPd може лише віддавати статичні файли, якщо так вирішить пакування.
- **LuCI** — не є UI системи; можливий додатковий пакет після 1.0.
- **simple-http-server** — розвивається як окремий проєкт і не є залежністю платформи.

### 3.6 Прошивки: офіційні релізи, локальна збірка, репозиторій на gateway

Окремого Build Server немає. Є три джерела образів і один шлях їх доставки.

```text
 ПК користувача                               Gateway
 ┌───────────────────────────────┐            ┌───────────────────────────┐
 │ smartnode build               │            │ Локальний репозиторій     │
 │  (PlatformIO або Docker-образ │  HTTP POST │ прошивок:                 │
 │   з зафіксованим toolchain)   ├───────────►│  образ + manifest + підпис│
 │ smartnode sign (ключ на ПК)   │            │  перевірка → OTA вузлам   │
 └───────────────────────────────┘            └───────────────────────────┘
                                                   ▲
 Офіційні релізи (CI → GitHub/GitLab Releases) ────┘ (імпорт через браузер)
```

| Сценарій | Джерело |
|---|---|
| Масові плати (ESP32, Pico W) | Офіційні стокові образи з CI; датчики налаштовуються без компіляції |
| STM32, власний код, нестандартні драйвери | Локальна збірка (`smartnode build` / Docker) → репозиторій на gateway |
| Збірка на іншій машині (домашній сервер, CI) | Той самий Docker-збирач; окремий Build Server API не потрібен |

**Принципи:**

- **Відтворюваність.** Офіційний Docker-образ збирача з зафіксованими версіями PlatformIO і toolchain. Той самий образ використовує CI, тож локальна й офіційна збірки ідентичні.
- **CLI розробника:** `smartnode keygen`, `smartnode build`, `smartnode sign`, `smartnode upload --gateway router.local`.
- **Підписування двома ключами.** Вузол довіряє ключу проєкту (офіційні релізи) і ключу користувача (генерується на ПК, публічна частина записується у вузол під час першого прошивання). Приватний ключ користувача **залишається на ПК**, не на gateway.
- **Gateway не звертається в інтернет.** Образи надходять ззовні: з браузера (імпорт релізу) або з CLI. Gateway лише перевіряє підпис і сумісність.
- **PlatformIO і toolchain не встановлюються на роутер.**

## 4. Основні сценарії

### 4.1 Перше підключення пристрою

1. Користувач відкриває сторінку «Add device» і підключає плату до ПК через USB.
2. Браузер через **Web Serial** записує стокову прошивку для обраної плати (ESP32 — через `esptool-js`; Pico W — UF2 «drag-and-drop», далі конфігурація через USB CDC).
3. Користувач обирає датчики й піни; сторінка перевіряє конфігурацію за описом плати.
4. Тим самим каналом передаються: SSID/пароль Wi-Fi, адреса gateway, **ключ вузла (PSK), згенерований gateway**, публічні ключі для перевірки прошивок, конфігурація датчиків.
5. Вузол підключається до Wi-Fi і **сам реєструється** на gateway з ідентифікатором `ep` (з MAC/chip-ID).
6. Gateway вже знає ключ і `ep` — вузол **довірений із моменту появи** і відображається на дашборді.

Обмеження: Web Serial працює в Chromium-браузерах і вимагає безпечного контексту (HTTPS або `localhost`). Резервний варіант — точка доступу (SoftAP) з captive portal на самому вузлі; ручне додавання адреси залишається завжди.

### 4.2 Читання датчика та керування

```text
Node    --POST /rd?ep=esp32-a1b2c3&lt=300 (link-format)-->  Gateway   реєстрація
Gateway --GET /sensors/temperature, Observe: 0---------->  Node      підписка
Gateway <--2.05 Content (SenML), далі нотифікації--------  Node
Browser <--SSE: event: resource, data: {...}-------------  Gateway   push у UI

Browser --PUT /api/v1/devices/{id}/resources/heater----->  Gateway
Gateway --PUT /actuators/heater------------------------->  Node
Gateway <--2.04 Changed----------------------------------  Node
Browser <--HTTP 200 + JSON-------------------------------  Gateway
```

Звичайні HTTP GET повертають значення з кешу gateway; CoAP-запит на кожен HTTP-запит не виконується.

### 4.3 Оновлення прошивки (pull-OTA)

```text
Browser/CLI -> Gateway: POST /api/v1/firmware (образ + маніфест)
Gateway: перевірка підпису, board/bootloader, sequence > поточного
Web UI: "Update available"
User -> Gateway: approve OTA
Gateway --PUT /system/update {uri, size, sha256, version}-------> Node
Node    --GET coap://gateway/fw/esp32/1.2.0.bin (Block2)--------> Gateway  (повторюється)
Node: перевірка SHA-256 і підпису, запис у неактивний слот, reboot
Node    --POST /rd/4521 (повторна реєстрація з новою версією)---> Gateway  = підтвердження
Gateway -> UI (SSE): success / error / rollback
```

Вузол керує темпом завантаження і може продовжити після обриву з потрібного блоку. На вузлі потрібен лише CoAP-клієнт з Block2.

Не кожна зміна потребує нової прошивки: датчики, піни, назва та інтервали змінюються через `PUT /system/config`.

### 4.4 Власна прошивка розробника

1. `smartnode keygen` — одноразово; публічний ключ записується у вузли під час provisioning.
2. `smartnode build --board pico_w` — збірка в Docker-збирачі або локальному PlatformIO.
3. `smartnode sign` → `smartnode upload --gateway router.local`.
4. Далі — стандартна pull-OTA (4.3) або перше прошивання через Web Serial (4.1).

## 5. Протоколи й API

### 5.1 CoAP Device Profile

Профіль складається зі стандартних частин; власна специфікація зводиться до словника значень `rt` і структури системних ресурсів.

| Потреба | Рішення |
|---|---|
| Тип ресурсу, інтерфейс | атрибути `rt` та `if` у CoRE Link Format (RFC 6690); `if="core.s"` — сенсор, `if="core.a"` — актуатор |
| Підтримка Observe | атрибут `obs` |
| Формат вимірювань і одиниці | **SenML** (RFC 8428): `n`, `v`, `vb`, `u`, `t`; зареєстровані одиниці (`Cel`, `%RH`, `V`…) |
| JSON чи CBOR | обидва через Content-Format SenML; JSON — за замовчуванням, CBOR — опція |
| Словник типів | значення `rt` з орієнтацією на IPSO Smart Objects (Temperature 3303, Humidity 3304, Light Control 3311…) |

Приклад `/.well-known/core` (і payload реєстрації):

```text
</sensors/temperature>;rt="temperature";if="core.s";obs;ct=110,
</sensors/humidity>;rt="humidity";if="core.s";obs;ct=110,
</actuators/relay>;rt="switch";if="core.a";ct=110,
</system/info>;rt="smarthome.info";ct=50,
</system/config>;rt="smarthome.config";ct=50,
</system/update>;rt="smarthome.update";ct=50
```

Значення ресурсу:

```json
[{"n":"temperature","u":"Cel","v":22.4}]
```

Системні ресурси:

```text
GET  /.well-known/core
GET  /system/info      ідентичність, плата, версія, ключі, можливості
GET  /system/config    поточна конфігурація датчиків
PUT  /system/config    нова конфігурація (перевіряється за описом плати)
PUT  /system/update    запуск pull-OTA
```

Приклад `/system/info`:

```json
{
  "ep": "esp32-a1b2c3",
  "board": "esp32dev",
  "target": "esp32",
  "firmware_version": "1.2.0",
  "sequence": 12,
  "bootloader": "1.0",
  "ota_supported": true,
  "trusted_keys": ["project-2026", "user-7a3f"]
}
```

### 5.2 Реєстрація вузлів (Resource Directory, RFC 9176)

```text
Node  --POST /rd?ep=esp32-a1b2c3&lt=300 (payload: link-format)-->  Gateway
Node  <--2.01 Created, Location: /rd/4521--------------------------  Gateway
Node  --POST /rd/4521 (кожні lt секунд, як heartbeat)------------->  Gateway
```

- `ep` — стабільний ідентифікатор вузла; IP не є ідентифікатором.
- Реєстрація без дійсного DTLS-PSK відхиляється.
- Відсутність оновлення протягом `lt` → вузол offline.
- Повторна реєстрація після OTA є підтвердженням нової версії.

### 5.3 HTTP API Gateway

**Продуктовий API** — логічні ресурси з валідацією та ACL:

```text
GET    /api/v1/devices
GET    /api/v1/devices/{id}
GET    /api/v1/devices/{id}/resources
GET    /api/v1/devices/{id}/resources/{name}
PUT    /api/v1/devices/{id}/resources/{name}
GET    /api/v1/devices/{id}/config
PUT    /api/v1/devices/{id}/config
POST   /api/v1/devices/provision          видача ep + PSK для нового вузла
DELETE /api/v1/devices/{id}
GET    /api/v1/events                     SSE-потік змін стану
```

**Репозиторій прошивок і OTA:**

```text
POST   /api/v1/firmware                   образ + маніфест (multipart)
GET    /api/v1/firmware?board=...         перелік образів
GET    /api/v1/firmware/{id}              деталі / маніфест
DELETE /api/v1/firmware/{id}
POST   /api/v1/devices/{id}/updates       запуск OTA
GET    /api/v1/devices/{id}/updates/{update_id}
```

**API розробника** (роль «розробник») — HTTP→CoAP-проксі для Resource Explorer, з відображенням за RFC 8075:

```text
ANY    /api/v1/dev/coap/{id}/{coap-path}
```

Вимоги: автентифікація, ролі, обмеження розміру payload, аудит керувальних операцій, асинхронна обробка (3.3.1).

### 5.4 Маніфест прошивки

Єдиний формат для будь-якого джерела (CI, локальна збірка, ручне завантаження), за мотивами IETF SUIT (RFC 9019, RFC 9124). На MVP — JSON, підписаний Ed25519:

```json
{
  "target": "esp32",
  "board": "esp32dev",
  "version": "1.2.0",
  "sequence": 12,
  "size": 1048576,
  "sha256": "9f2c…",
  "min_bootloader": "1.0",
  "key_id": "user-7a3f",
  "signature": "base64…"
}
```

- `target`/`board` — перевірка сумісності (аналог vendor/class ID у SUIT);
- `sequence` — монотонний номер для захисту від downgrade;
- `key_id` — який із довірених ключів підписав образ.

## 6. Реєстрація, Observe, OTA

**Поява пристроїв:** основний механізм — самореєстрація (5.2); адреса gateway задається під час provisioning. CoAP multicast і mDNS — опційний резерв (можуть не проходити через VLAN, ізоляцію Wi-Fi та маршрутизовані мережі). Ручне додавання адреси — завжди.

**Ресурси:** перелік надходить у payload реєстрації; `/.well-known/core` використовується для повторної синхронізації.

**Observe:** одна підписка gateway на ресурс, кеш станів, повторна підписка після збоїв або нової реєстрації, позначка застарілих значень. Observe не гарантує доставку кожного проміжного вимірювання.

**OTA:** pull-модель через Block2 (4.3), підписані образи, перевірка сумісності й цілісності, A/B-слоти, підтвердження через повторну реєстрацію, rollback там, де його підтримує платформа. Початкове програмування не входить до OTA — для нього є Web Serial (4.1).

## 7. Безпека

| Етап | Транспорт CoAP | Обґрунтування |
|---|---|---|
| MVP | **DTLS 1.2 з PSK** на кожен вузол; ключ видається під час provisioning | Простий, підтримується mbedTLS на ESP32/Pico; без інфраструктури сертифікатів |
| Після 1.0 | **OSCORE** (RFC 8613) + **EDHOC** (RFC 9528) | Захист на рівні повідомлень, працює через проксі, легший для обмежених вузлів |

- **Модель довіри:** вузол без дійсного ключа не може зареєструватися — недовірені вузли відсіюються на вході і не керують виконавчими ресурсами.
- **Прошивки:** підпис Ed25519 незалежний від транспорту; два довірені ключі (проєкту й користувача); приватний ключ користувача — тільки на ПК; захист від downgrade через `sequence`; журнал оновлень.
- **Web UI і HTTP API:** автентифікація, ролі (адміністратор, розробник, користувач) і ACL; доступ лише з LAN за замовчуванням; root-доступ до LuCI не потрібен.
- **HTTPS:** самопідписаний сертифікат лякає користувачів, але Web Serial потребує безпечного контексту. Варіанти: HTTPS на gateway з можливістю завантажити власний сертифікат, або сторінка першого прошивання на HTTPS-сайті проєкту. Остаточний вибір — у відкритих рішеннях.
- **Gateway на OpenWrt:** мінімальні права daemon, окремий користувач, безпечна конфігурація firewall, без вихідного доступу в інтернет.

## 8. Платформи

| Платформа | Статус | Коментар |
|---|---|---|
| **ESP32** | MVP, повна підтримка | Штатний A/B OTA з rollback в ESP-IDF, Wi-Fi, mbedTLS, достатньо Flash для всіх стокових драйверів |
| **Pico W** | 1.0, без OTA | Стокова прошивка й Web Serial-конфігурація; оновлення через UF2. OTA потребує власного bootloader з двома слотами — після 1.0 |
| **STM32** | після 1.0 | Більшість STM32 не мають мережі — потрібен Ethernet (вбудований MAC, W5500) або Wi-Fi-співпроцесор; мала Flash → власна збірка замість стокової |

## 9. Розгортання й пакування

### 9.1 OpenWrt

```text
libcoapcpp     — універсальна бібліотека
coap-manager   — C++ gateway / HTTP API / SSE / UI assets / репозиторій прошивок
```

`luci-app-coap-manager` — після 1.0. Gateway запускається через `procd`, конфігурація інтегрується з UCI. Для публікації: `openwrt/packages`. Пакети збираються cross-toolchain/SDK; враховується різниця пакетних менеджерів (APK / OPKG) між версіями OpenWrt.

**Нефункціональна вимога:** зафіксувати бюджет пам'яті (орієнтовно пакет ≤ 1 МБ, RSS ≤ 10 МБ) і перевіряти його на цільових роутерах із 16 МБ Flash / 128 МБ RAM з урахуванням `libstdc++`, CivetWeb і mbedTLS.

### 9.2 Звичайний Linux

Той самий `coap-manager` і Web UI; systemd service або Docker-контейнер. Дозволяє розробляти й тестувати MVP на Ubuntu без очікування пакування для OpenWrt.

### 9.3 Інструменти збирання прошивок

- Офіційний Docker-образ збирача з зафіксованими версіями PlatformIO/toolchain.
- CI проєкту збирає стокові образи для всіх підтримуваних плат тим самим образом і публікує їх у Releases.
- CLI `smartnode` для розробників (keygen, build, sign, upload).

### MVP scope — що робимо першим

- Один процес `coap-manager` на Ubuntu/Linux; бізнес-логіка не прив'язана до OpenWrt.
- CivetWeb, один CoAP-потік, SSE.
- ESP32 + BME280 + реле; простий вебінтерфейс.
- CoAP GET/PUT, Observe, самореєстрація, SenML.
- Після підтвердження схеми — стокова прошивка, provisioning, OTA, локальна збірка.

## 11. Відкриті рішення

**Закриті у v0.2:**

| Питання v0.1 | Рішення |
|---|---|
| HTTP backend і паралелізм | CivetWeb + один CoAP event loop + черга команд + снапшот стану (3.3.1) |
| Специфікація профілю пристрою | `rt`/`if`/`obs` + SenML + словник `rt` (5.1) |
| JSON чи CBOR | SenML в обох; JSON за замовчуванням |
| Provisioning Wi-Fi і ключів | Web Serial під час першого прошивання; ключ генерує gateway (4.1) |
| Схема OTA | Pull через Block2, A/B-слоти, маніфест за мотивами SUIT (4.3, 5.4) |
| Перші MCU | ESP32 — повністю; Pico W — без OTA; STM32 — після 1.0 (8) |
| Підпис маніфесту | Ed25519, ключі проєкту й користувача, `sequence` проти downgrade |
| Зберігання історії | RAM-буфер; історія — через експорт (3.3.2) |
| Build Server і його фінансування | Не потрібен: стокова прошивка + локальна збірка (3.6) |

**Залишаються відкритими:**

1. Фінальна назва проєкту; ліцензії (рекомендація: Apache-2.0 або MIT для `libcoapcpp` і SDK).
2. Повний словник значень `rt` і JSON-схема конфігурації датчиків.
3. Розміщення сторінки першого прошивання: HTTPS на gateway чи HTTPS-сайт проєкту (вимога безпечного контексту Web Serial).
4. Скільки версій образів зберігати на gateway і чи підтримувати USB-сховище.
5. Bootloader з двома слотами для Pico W.
6. Мережевий стек і перелік плат для STM32.
7. Шлях міграції з DTLS-PSK на OSCORE/EDHOC.
8. Інтеграції після MVP: MQTT-міст із Home Assistant MQTT Discovery, графіки, правила автоматизації.
